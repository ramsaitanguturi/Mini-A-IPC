Approximately 0.66–2.59 microseconds for smaller payloads in the latest trials, compared with roughly 100–250 microseconds for many userspace mechanisms.

This is promising, but it has not yet been established that the kernel and userspace implementations measure equivalent operations.

Inspect:

- `kernel/aipc_module.c`
- Kernel mailbox userspace client
- `src/` implementations
- Kernel benchmark scripts
- Timing boundaries
- Synchronization
- Data copying
- Payload validation
- Request/response semantics

### Perform a measurement-equivalence audit

For every IPC mechanism, document:

1. What constitutes one exchange?
2. Is the measurement a one-way transfer or a complete round trip?
3. Does it include producer and consumer synchronization?
4. Does it include system calls?
5. Does it include user-to-kernel copying?
6. Does it include kernel-to-user copying?
7. Does it include response generation?
8. Does it include payload validation?
9. Does it include process wakeups and scheduling?
10. Does it include initialization or cleanup?

Compare equivalent operations only.

If the kernel mailbox uses a different measurement boundary, correct the benchmark so that the comparison is fair.

Do not artificially add arbitrary delays to the kernel implementation.

If the kernel mailbox is fundamentally measuring a different operation, report it separately instead of presenting an invalid direct comparison.

## 4. Critical issue: adaptive transport selection

The adaptive implementation currently performs inconsistently and frequently loses to pipes.

Examples from Trial 2:

| Payload | Adaptive latency | Pipe latency |
|---|---:|---:|
| 64 B | 324.41 us | 112.32 us |
| 256 B | 245.40 us | 111.60 us |
| 1 KB | 200.09 us | 107.31 us |
| 16 KB | 210.52 us | 125.05 us |

Previous investigation found that `src/selector.c` uses a simple threshold-based policy:

- Small payloads select shared memory.
- Large payloads select pipes.

However, previous optimization output showed adaptive routing selecting pipes for every tested payload.

Investigate this discrepancy.

Inspect:

- `src/selector.c`
- `src/mixed_benchmark.c`
- Adaptive CLI implementation
- Threshold arguments
- Default configuration
- Build dependencies
- Benchmark scripts
- Actual runtime transport selection

### Required corrections

1. Verify that the executable is built from the latest source.
2. Verify that the threshold passed by the benchmark is actually applied.
3. Verify that the selector returns the expected mechanism.
4. Add explicit transport-selection logging in diagnostic mode.
5. Ensure the adaptive implementation does not initialize unused transports unnecessarily.
6. Avoid unnecessary allocations and IPC setup for each message.
7. Avoid repeating expensive selector operations when the decision can safely be reused.
8. Measure selector overhead separately from transport overhead.
9. Test boundary conditions around the threshold.
10. Ensure large payloads never exceed SHM capacity.

Do not assume SHM is always faster for small messages.

Use measured results to choose a threshold. If pipes outperform SHM under the tested environment, the policy should reflect that.

### Adaptive policy requirements

Create a reproducible comparison of:

- Always PIPE
- Always SHM where supported
- Fixed threshold policy
- Improved adaptive policy

Use identical workloads and message counts.

The adaptive implementation must not claim superiority unless it demonstrates it statistically.

If adaptive routing cannot beat the best fixed mechanism, report that honestly.

## 5. Shared-memory synchronization investigation

The current shared-memory implementation uses process-shared semaphores and a request/response mailbox.

Previous optimization experiments showed:

- Faster semaphore waiting appeared to reduce latency by approximately 13–19%.
- Cache-line alignment produced inconsistent results.
- The experimental SPSC ring buffer was slower than the existing semaphore implementation.

Investigate the implementation rather than blindly applying optimizations.

Inspect:

- `src/ipc_shm.c`
- Shared-memory structures
- Semaphore initialization
- Semaphore wait functions
- Producer/consumer synchronization
- Memory ordering
- Cache-line placement
- Child-process monitoring
- Cleanup and failure handling

### Required work

1. Identify unnecessary semaphore waits and wakeups.
2. Identify polling or timeout overhead.
3. Identify possible false sharing.
4. Verify memory ordering and synchronization correctness.
5. Verify that fast waiting does not remove important child-death detection.
6. Preserve correct cleanup and error handling.
7. Compare the current implementation with the optimized implementation.
8. Retain only optimizations that demonstrate a reproducible benefit.

Do not remove safety checks simply to improve benchmark numbers.

Do not introduce busy-waiting without measuring CPU consumption and considering scheduling behavior.

Do not replace the existing implementation with the ring buffer unless it demonstrates a genuine improvement.
