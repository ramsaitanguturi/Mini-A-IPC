# 1. Project overview

The project currently implements and compares these IPC mechanisms:

1. Anonymous Pipes
2. Named Pipes (FIFO)
3. System V Message Queues
4. POSIX Message Queues
5. POSIX Shared Memory with process-shared semaphores
6. Unix Domain Sockets

It also implements an adaptive IPC selector that chooses between shared memory and pipes based on payload size.

Important source files:

- `src/ipc_pipe.c`
- `src/ipc_fifo.c`
- `src/ipc_sysv_mq.c`

- `src/main.c`
- `src/mixed_benchmark.c`
- `include/ipc.h`
- `kernel/aipc_module.c`
- `bench/`

The project also includes correctness tests, benchmarking scripts, syscall profiling, and report-generation scripts.

# 4. Important problems discovered in the current implementation

## Problem A: Semaphore monitoring overhead

Inspect `src/ipc_shm.c`.

The function:

`sem_wait_monitor_child()`

uses:

- `clock_gettime(CLOCK_REALTIME)`
- `sem_timedwait()`
- A 100 ms timeout.
- `waitpid(..., WNOHANG)` when the timeout expires.

The parent calls this function twice per exchange:

1. Waiting for `request_empty`.
2. Waiting for `response_full`.

For 10,000 exchanges, that means approximately 20,000 calls to the monitoring wrapper and its associated clock-read/deadline logic, excluding retries and other operations.

This is part of the timed benchmark loop.

The child uses `sem_wait_retry()`, which simply waits on a semaphore and retries on EINTR.

### Required investigation

Determine how much overhead the parent-side child-monitoring mechanism contributes.

Implement a controlled benchmark variant that uses ordinary `sem_wait_retry()` during normal timed execution.

Keep the robust child-monitoring implementation available for failure-handling tests.

Do not permanently remove child-failure handling.

Use an external timeout during the experimental benchmark, for example:

`timeout 30s ./mini-aipc --mode shm --size 64 --count 10000`

Make sure the normal and experimental versions are tested under identical conditions.

Compare:

- Average RTT.
- Median RTT.
- P95 and P99 RTT.
- Throughput.
- Validation errors.
- Child crash behavior.

Do not assume every `sem_timedwait()` call necessarily produces a kernel syscall. Measure the actual overhead.

## Problem B: Four process-shared semaphores

The current mailbox structure is:

```c
typedef struct {
    sem_t request_empty;
    sem_t request_full;
    sem_t response_empty;
    sem_t response_full;
    size_t request_length;
    size_t response_length;
    unsigned char request[SHM_MAX_PAYLOAD];
    unsigned char response[SHM_MAX_PAYLOAD];
} shared_mailbox_t;
```

The parent and child coordinate through four process-shared semaphores.

The current request-response protocol is correct in principle, but synchronization overhead may be affecting performance.

Investigate:

- Semaphore wake-up overhead.
- Futex usage.
- Context switching.
- Cache-line contention.
- Producer/consumer synchronization.
- Memory-copy overhead.
- Whether all four semaphores are necessary.

Do not remove synchronization primitives without proving that correctness and memory ordering are preserved.

## Problem C: Cache-line contention

The current shared mailbox places synchronization objects close together.

Investigate whether producer and consumer frequently modify data sharing the same cache line.

Experiment with cache-line-separated synchronization data.

A possible experimental layout is:

```c
#define CACHE_LINE 64

typedef struct {
    _Alignas(CACHE_LINE) sem_t request_empty;
    sem_t response_full;

    _Alignas(CACHE_LINE) sem_t request_full;
    sem_t response_empty;

    size_t request_length;
    size_t response_length;

    unsigned char request[SHM_MAX_PAYLOAD];
    unsigned char response[SHM_MAX_PAYLOAD];
} shared_mailbox_t;
```

This is only a starting experiment.

Verify actual field offsets, alignment, structure size, and cache-line placement.

Do not assume that adding `_Alignas(64)` automatically eliminates false sharing.

Measure the effect before accepting this change.

## Problem D: Current SHM implementation uses POSIX semaphores

The source uses:

- `sem_init()`
- `sem_wait()`
- `sem_timedwait()`
- `sem_post()`
- `sem_destroy()`

The syscall profile recorded futex activity.

Explain how POSIX semaphores can use futex operations internally on Linux.

Do not introduce explicit futex system calls without a strong reason.

First investigate whether the existing semaphore implementation is the actual bottleneck.

# 5. Current adaptive selector problem

Inspect `src/selector.c` and `include/ipc.h`.

Current definitions:

```c
#define SHM_MAX_PAYLOAD 1024U
#define DEFAULT_THRESHOLD 1024U
```

Current selector:

```c
transport_t select_transport(size_t payload_size, size_t threshold)
{
    if (payload_size <= threshold && payload_size <= SHM_MAX_PAYLOAD)
        return TRANSPORT_SHM;

    return TRANSPORT_PIPE;
}
```

Current behavior:

| Payload | Selected mechanism |
|---:|---|
| 64 B | SHM |
| 128 B | SHM |
| 256 B | SHM |
| 512 B | SHM |
| 1024 B | SHM |
| Above 1024 B | PIPE |

This is a fixed size-based selector.

It does not use telemetry, measured performance, workload history, or dynamic adaptation.

The source comment explicitly acknowledges that it is not the paper's full adaptive telemetry/hysteresis controller.

### Required improvement

Do not immediately change the default threshold.

First optimize SHM and repeat the measurements.

Then investigate a more defensible adaptive policy.

Potential improvements:

1. Calibrate the crossover point using measured performance.
2. Use separate thresholds for different workload conditions if supported by evidence.
3. Add telemetry for latency and throughput.
4. Investigate an EWMA-based performance estimator.
5. Consider hysteresis to prevent rapid switching between mechanisms.
6. Ensure selection overhead does not exceed the benefit gained.
7. Retain a simple fallback policy.

Do not claim the selector is dynamically adaptive unless it actually measures and responds to performance.


The workload consists of:

- 64-byte messages use SHM under the adaptive policy.

This is a useful experiment because both policies receive the same workload sequence.
